# 10 · Decision Log

Short ADRs. Add a new entry whenever the architecture or a major dependency changes. Status: Accepted unless noted.

## ADR-001 · Clean Architecture with three layers
**Context:** The app must stay testable and swappable (storage, PDF engine, editor) over a long life.
**Decision:** `domain` / `data` / `presentation` with inward dependencies and a composition root in `app/`. Boundaries enforced by lint.
**Consequences:** More files and mappers; in return, domain logic is testable without a browser and adapters are replaceable.

## ADR-002 · Local-first storage with IndexedDB (Dexie)
**Context:** Single newsroom, daily use, likely one machine; no backend specified.
**Decision:** Persist in IndexedDB through Dexie behind repository ports; bundle export/import for backup and transfer.
**Consequences:** Works offline, zero infrastructure. Browser storage can be cleared, so backup export is a first-class feature. A remote adapter can be added later without touching use cases.

## ADR-003 · TipTap for the rich-text editor
**Context:** Need structured rich text, custom nodes, and native Telugu IME support.
**Decision:** TipTap (ProseMirror) inside the presentation layer only; domain stores an editor-agnostic `ArticleBody`.
**Alternatives:** Lexical (good, less mature extension ecosystem for our needs), Slate (more manual work), Quill (weaker schema).
**Consequences:** One mapper to maintain; editor replaceable.

## ADR-004 · PDF generated by Chromium, not a JS PDF library
**Context:** Telugu needs complex-script shaping; A3 multi-column layout is easiest in CSS.
**Decision:** Render pages with CSS (`@page` A3, mm units) and produce the PDF with Chromium (browser print first, Playwright companion later) behind a `PdfExporter` port.
**Alternatives:** jsPDF / pdf-lib / pdfmake (shaping of Telugu unreliable), `@react-pdf/renderer` (limited Indic shaping and multi-column), server-side LaTeX/XeTeX (excellent shaping, but a separate layout system and no preview parity).
**Consequences:** Preview equals output. Phase 1 relies on the print dialog; Phase 2 removes it with the companion.

## ADR-005 · Millimetre-based layout on a 6-column grid
**Context:** Print output must be exact.
**Decision:** Page geometry in mm everywhere; grid of 6 columns, 4 mm gutter, 10 mm vertical module.
**Consequences:** Canvas is scaled via CSS transform for display only.

## ADR-006 · State management: TanStack Query + Zustand
**Context:** Data comes from async use cases; UI has ephemeral state.
**Decision:** TanStack Query caches use-case results; Zustand holds UI state per feature.
**Consequences:** Two small libraries with clear roles; no global store.

## ADR-007 · Bilingual UI via i18next
**Decision:** UI strings in `en.json` and `te.json`, CI-checked for parity. Content language is independent of UI language.

## ADR-008 · Self-hosted open fonts
**Decision:** Bundle OFL fonts (Noto family, Source Serif 4, Playfair Display, Inter) via Fontsource; no runtime CDN.
**Consequences:** Offline-safe and reproducible PDFs. Licences must be reviewed before adding any other typeface.

## ADR-009 · shadcn/ui as owned source
**Decision:** Components are copied into `presentation/components/ui/`, themed with CSS variables, and kept free of business logic.

## ADR-010 · Package manager and tooling
**Decision:** pnpm, Vite, Vitest, Playwright, ESLint with boundaries plugin, Prettier, Conventional Commits.
